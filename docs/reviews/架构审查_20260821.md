## 2. 分层评估（逐层实测）

### 2.1 桌面壳 desktop_app.py（805 行）✅ 健康
- uvicorn 子进程拉起 FastAPI，真 SPA 加载，热键/OCR 区域监听独立于主线程。
- 单实例锁 + 端口清理：反复重启不留孤儿（此前修过）。
- 职责单一清晰，无越层。

### 2.2 API 层 server/main.py（2074 行）⚠️ 单片路由
- **优点**：鉴权分工清晰（`require_emp` / `require_admin` / `require_emp_local` / `require_license_active` 四级）；进程级引擎单例 + `_ENGINE_LOCK` 避免每请求重建（已修 E2）；限流 + 安全头中间件都在。
- **债**：2000+ 行把所有域（account / ris / ocr / screen / queue / settings / rules / update / sample 导入导出）**堆在一个文件**。接口约 50 个，已明显超"单片所能承受"的规模。
- 典型症状：`RisConfigReq`、`SampleCreate`、`OCRB64`、`SampleImportReq` 等 Pydantic 模型与应用路由混排，多个 route handler 内部又揉入业务逻辑（如 `_ris_poll_once_locked` 758 行、`_queue_add_text` 833 行）。

**建议（P2）**：拆成 `server/routes/` 子包 + 各自路由描述，main.py 只做 `include_router` 与中间件装配。模型抽 `server/schemas.py`。这是最干净、风险最低的拆分。

### 2.3 质控引擎 engine.py（2486 行）⚠️ 单片单片 + 隐藏循环依赖风险
- **优点**：`RuleEngine.run()` 调度清晰（18 条规则线性追加 + 2 条可选），`_dedup_findings` 跨规则去重，配置化开关（enable_r16/r19）已落地，规则内置大量注释说明派生关系。
- **债（结构性）**：
  1. **类与模块级函数混杂**：`RuleEngine`（规则）+ `ChineseRadiologyNER`（NER）+ `_KG`（知识图谱）+ 一堆模块级 helper（`_r5_fam`、`_dedup_findings`、`score`）。三者职责本可拆 `engine_rules.py` / `ner.py` / `kg.py`，当前挤在一个 2486 行文件。
  2. **数据源分散**：`REGION_TO_ORGANS`（199 行）、`REPORT_TYPE_REQUIREMENTS`（222）、`_REGION_KW_RE`（292）、`ORGAN_SIDE_LIST`（474）……词表/元数据与逻辑硬编码同文件，改词表直接动引擎。
  3. **段落切分重复实现**：`ChineseRadiologyNER._split_sections`（956 行）与 `_split_for_r5`（1341 行）用同一 `_FINDINGS_HEADERS`/`_IMPRESSION_HEADERS` 各写一遍；句子切分又在 `engine_text._split_sentences`（118）。三处 section 解析，往后改一处容易漏同步。
- **优点**：仍能以代码为准改动，270 测试兜底，`run()` 只读 `self.rules_config`，并发安全。

**建议（P2，渐进不重构）**：不一次性推翻。先做**低风险抽离**：① `_lexicons.py`/`anatomy_lexicon.py` 已承担大词表，把 `REGION_*`/`REPORT_TYPE_REQUIREMENTS` 也迁入词表模块；② 统一三处 section 切分收敛到一个 `_sectionize()` 供 NER 与 R5 共用；③ 暂不动 R1-R23 逻辑本身。

### 2.4 数据层 server/db.py + src/samplelib.py ⚠️ 双轨并存（收敛中）
- **server/db.py（160 行，健康）**：SQLAlchemy，`DATABASE_URL` 切 PG，SQLite 用 `BEGIN IMMEDIATE` + `busy_timeout` 把复合操作串行化防并发首访——**并发处理是对的**。迁移函数（settings 复合唯一索引、queue hash）幂等且手工 SQL，应对 create_all 不迁移存量表的现实。
- **src/samplelib.py（924 行，债）**：仍用 **raw `sqlite3`**，虽已收敛到同库 `qc.db`，但 API 与传统 ORM 不一致；迁移旧 samples.db 也用手工 sqlite3。造成 `server/db.py`（ORM）+ `samplelib.py`（裸 sqlite3）同库双访问，事务语义与列定义各管各，改 schema 需两处同步。
- **accounts.py（303 行）**：正确使用 `from server import db, models` + `SessionLocal`，走在 ORM 轨上——与 samplelib 形成鲜明对比。

**建议（P1，影响 DB 前置 MVP）**：`samplelib.py` 全面迁移到同一 `SessionLocal`/`declarative_base`（samples 表已由 `models.py` 声明），删掉裸 `sqlite3` 连接与迁移里手写的 SQL，让整个库只有一个 schema 真相源。这是 GTM 多用户共享样本库的前置条件。

## 3. 性能实测（本地 Mac，托管 python 3.13）
| 指标 | 值 | 评价 |
|---|---|---|
| 引擎 import + 实例化 | 0.18 s | 冷启一次即可,进程级单例缓存 |
| 单条 run()（典型报告,200 次） | avg **39.4 ms/次** | 远低于百ms阈值,对 50 条批量(≈2s)可接受 |
| 全量测试 | **270 passed / 7 skipped / 9 subtests, 7.16s** | 健康 |

- `ChineseNER` 每次 `run()` 新建实例但**无重模型加载**（纯词典正则），故 39ms 主要花在正则遍历 18 规则——合理，非热点。
- 批量 50 条 ≈ 2s 串行，可接受；若要快可并行化，但**优先级低**。

| 级别 | 问题 | 影响 | 处置 |
