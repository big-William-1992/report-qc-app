## 0. 阅读指引

### 0.1 本文件是什么、不是什么

**是**：一份把"监管要求"拆成可核查条目的差距清单，用于判断**先做什么、谁来定、要多久、花在哪**。

**不是**：

- 不是法律意见书，不构成合规结论；
- 不是注册申报资料，也不是等保测评报告；
- **未做**法规条款级精确引用。文中出现的法规/标准名称、标准号均为公开可查的名称与编号；**凡涉及具体适用条款、阈值、判定口径之处，一律标注"需专业机构确认"**，请勿把本文当作法条依据。

> **通用免责**：中国医疗器械与网络安全法规更新频繁，本文所列法规/标准**均以最新有效版本为准**；标准号若已废止或修订，以现行版本为准。

### 0.3 一页纸结论（给创始人）

1. **最紧迫的不是等保，而是"定位口径不自洽"。** 仓库内 `docs/DISCLAIMER.md` 写"明确为科研/教学辅助用途，**非医疗器械**"，而 `README.md` 写"涉及二类医疗器械……请完成注册与测评"。同一产品对外两种口径，是本文识别的**最高优先级风险**（详见 §2、§3.0）。对外材料必须收敛到一句话的用途声明。
2. **若坚持"不输出诊断结论、仅做质量核查与台账"并全程默认本地，存在按非器械定位先商用的现实路径**，但**该判定必须由器械注册顾问/律师确认**，不能由内部自行认定（详见 §2）。
3. **等保三级大概率不是唯一选项。** 系统定级需按现行定级标准判定；若本系统仅为院内单机/科室内辅助工具、不构成关键信息基础设施、不影响核心诊疗业务连续性，是否必须三级、还是二级即可，**需定级专家与测评机构确认**（详见 §1、§4）。
4. **数据合规上最大的两个具体窟窿是"备份不加密"和"报告正文可能进日志/诊断包"**，这两项与是否做器械注册无关，**任何路线下都该先补**（详见 §5）。
5. **器械注册的现实周期应按 12–24 个月规划**，把"12 个月拿证"当承诺是危险的（详见 §6 路线 B）。

## 5. 数据合规与 PHI 专项

> 本章是**无论走哪条路线都必须做**的部分。PIPL 下医疗健康信息属**敏感个人信息**，处理门槛高于一般个人信息；本项目处理的是真实患者报告正文，属于"处理敏感个人信息"。

### 5.1 数据分级建议

| 级别 | 数据类别 | 具体内容（映射本项目） | 敏感度 | 建议保护要求 |
|------|----------|----------------------|--------|-------------|
| **L1 患者直接标识** | 可单独识别个人的信息 | 姓名、住院号/门诊号、身份证号、电话、DICOM 患者 ID（若进入样本库） | 敏感个人信息（最高） | 不采集或即刻去标识；如必须存储则字段级加密；访问须审批；日志与导出**绝对禁止**出现 |
| **L2 报告正文（含 PHI）** | 诊疗内容 | `qc.db` 样本库报告文本、`feedback.db` 医生反馈正文、RIS/PACS 拉取缓存、备份文件、诊断包（含 patient-data 时） | 敏感个人信息 | 存储加密；导出需审批与留痕；备份加密 + 介质登记；禁止出境 |
| **L3 质控结果与统计** | 派生的分析结果 | 质控发现、评分、扣分明细、错误类型分布、科室报表 | 中（可间接识别） | 单条结果按 L2 处理；**聚合统计**在小样本下可复原个体，需做最小分组阈值（如 n<5 不展示） |
| **L4 日志与诊断包** | 运维与排障数据 | `logs/` JSONL、`audit_log` 表、错误日志、诊断包 | 中–高（取决于擦洗效果） | 审计日志按 L2 保护；错误日志只留错误码/堆栈/白名单键；诊断包默认脱敏、默认剔除 `feedback.db` |
| **L5 系统与授权数据** | 系统运行数据 | 账号凭据（PBKDF2 散列）、科室、设置、订单、`license.dat`、机器指纹 | 中 | 凭据不可逆存储；`license.dat` 0600；订单数据涉及个人信息（客户联系人）需单独说明 |
| 说明 | — | 《数据安全法》语境下的"重要数据"认定 | ⚪ **本产品数据是否构成"重要数据"，需专业机构确认**；在未确认前，按最严假设（L1/L2 不出本机/院内）执行 | — |

**分级落地的三个硬要求**：

1. 分级必须**写进制度文档**并在代码中以常量/策略体现，否则无法向医院与测评机构举证。
2. L1/L2 **默认不出设备**；任何出设备行为（导出、诊断包、云端 LLM）都必须"默认拒绝 + 显式开启 + 留痕"。
3. L3 聚合报表需**小样本保护**，避免"统计结果反推个体"。

### 5.2 最小必要与脱敏要求

| 要求 | 说明 | 与本项目的动作 |
|------|------|---------------|
| 目的限定 | 处理患者报告的唯一目的是"报告质量核查"，不得用于训练、分析、画像、二次商业利用 | 在隐私政策、合同、UI 中写明；**禁止**将院内报告用于模型微调，除非有单独授权与伦理审批 |
| 最小必要 | 只处理质控所需字段；不需要身份证/电话/影像 | ✅ 现状已不采集身份证、手机号、DICOM 影像。保留此边界并写入文档 |
| 去标识化 | 入库/导出时移除姓名等直接标识 | 🟡 现状有"入库可选脱敏（去姓名）"。**建议改为默认脱敏**，取消"可选"；补充住院号/日期/机构名等间接标识 |
| 单独同意 | 处理敏感个人信息需单独同意 | ⚪ 本地部署时通常由医院作为控制者履行告知同意义务；**厂商侧应提供"告知同意文本"素材**，避免让医院裸奔。需律师确认责任分配 |
| 假名化与可逆性 | 若使用假名映射表，映射表必须与数据分离存储并加密 | ❌ 现状无假名机制，建议评估是否需要 |
| 脱敏的"不可逆"验证 | 需证明脱敏后的数据不能复原 | ❌ 无验证方法；建议对导出文件做抽样复核 + 记录 |

### 5.3 日志与诊断包红线

> 本节是本文最具体的行动清单，全部可在 1–3 周内完成。

| # | 红线 | 现状 | 必须做到 |
|---|------|------|----------|
| R-1 | 错误日志**不得**写入报告正文、反馈正文、患者标识 | 🟡 曾写入反馈正文；现已白名单键 + 粗粒度擦洗；官方口径"降低风险而非保证无 PHI" | ① 将"禁止字段清单"写成代码级校验（含单测），未知键直接丢弃；② 记录内容限于：时间、版本、错误码、异常类型、堆栈摘要、非 PHI 的上下文计数；③ 在日志文件头写入"本文件不含患者数据"的数据字典说明；④ 明确对历史日志的处理（提供清理指引） |
| R-2 | 诊断包默认**不含** `feedback.db` 等含完整报告正文的数据 | ✅ `export_diagnostic_bundle` 默认排除；`--include-patient-data` 才纳入；包内附隐私 README | ① 把"附隐私提示"升级为"附数据清单 + 接收方保密要求 + 保留期限"；② 含患者数据的诊断包**必须加密**（随机口令，口令走另一通道传递）；③ 导出动作写审计日志；④ 记录接收方与用途 |
| R-3 | 审计日志只增不改、不可删除 | 🟡 有 `audit_log` 表（21 个敏感端点） | ① 应用层不提供删除接口；② 加完整性校验（HMAC/哈希链）；③ 留存 ≥ 6 个月；④ admin 操作自身也被记录 |
| R-4 | 日志与诊断包**不得**离开院内网络 | ✅ 远程上报未实现；模块不联网 | 保持；在文档中明确"未实现远程上报"是**特性而非缺陷**，并防止未来误加 |
| R-5 | 崩溃转储/截图不得含报告区域 | ⚪ 未确认 | 核实崩溃导出、OCR 截图缓存、剪贴板历史是否落盘；如落盘需清理策略 |
| R-6 | 剪贴板监听的数据不得留存 | 🟡 有剪贴板轮询（≥15 字触发质控） | 核实是否落盘、是否进样本库、是否可在内存外残留 |

### 5.4 备份介质与销毁

| 项 | 现状 | 建议要求 |
|----|------|----------|
| 备份内容 | 含完整报告正文（`VACUUM INTO`） | 保持功能，但**必须加密**；考虑对报告正文做字段级加密后再备份 |
| 备份加密 | ❌ 无 | 引入密码技术加密（密钥不入同一介质）；密钥托管与轮换规程 |
| 备份位置 | 本机 | 增加离线/异地副本（院内合规介质），形成"3-2-1"思路的中式落地 |
| 保留期限 | 7/30/90 天三级轮转 | 明确期限依据（结合病历保管规定与医院要求）；到期**自动**清理并留痕 |
| 介质登记 | ❌ 无 | 备份介质/U 盘/移动硬盘需登记（编号、责任人、存放位置） |
| 介质销毁 | ❌ 无 | 销毁需记录（时间、介质编号、方式、见证人）；提供"数据彻底清除"工具 |
| 恢复演练 | ❌ 无 | 至少每季度一次恢复演练并留档 |
| 云端备份 | 未使用 | 若未来启用，需单独评估（数据出境、委托处理、医院审批） |

### 5.5 对外提供数据的审批流

> 原则：**默认禁止**；任何对外提供（导出给第三方、支持厂商远程排障、提供样例数据、用于微调/评测、发给云端 LLM）都必须走审批。

| 步骤 | 动作 | 责任人 | 输出物 |
|------|------|--------|--------|
| 1 | 提出需求：说明目的、数据范围、接收方、期限 | 需求方 | 数据提供申请单 |
| 2 | 必要性审查：能否用不带 PHI 的数据/合成数据替代 | 数据合规负责人 | 替代方案结论（优先用替代） |
| 3 | 最小化处理：去标识化 + 抽样 + 字段裁剪 | 技术负责人 | 脱敏记录 + 处理脚本版本 |
| 4 | 合规审查：法律依据、合同/DPA、告知同意是否覆盖 | 律师/法务 | 审查意见 |
| 5 | 医院审批（如数据来自医院） | 医院信息科 + 数据/伦理管理部门 | 书面批准 |
| 6 | 技术防护：加密（独立口令）、水印、访问限制 | 技术负责人 | 加密包 + 口令分通道传递 |
| 7 | 留痕：登记接收方、用途、期限，写入审计日志 | 数据合规负责人 | 数据提供台账 |
| 8 | 到期回收与删除确认 | 数据合规负责人 | 删除确认记录 |
| 9 | **禁止**事项：不得提供 `feedback.db` 原库、不得提供未加密备份、不得提供含直接标识的记录、不得用于训练未授权数据 | 全体 | — |

**当前可立即执行的简化版**（团队小、无专职合规）：把步骤 1–4 合为一张"数据导出审批表"（一页纸，含 8 个勾选项），由创始人与技术负责人双签，导出动作自动写审计日志。**先把"留痕"做起来，比先把流程做完美更重要。**

### 5.6 跨境与云端 LLM 的禁区

| 场景 | 现状 | 判定 | 要求 |
|------|------|------|------|
| 默认运行 | 本地推理，不联网 | ✅ 合规友好 | 保持；把"默认本地、数据不出院"固化为**技术强制**而非仅配置提示（如：未显式配置时云端 LLM 代码路径不可达） |
| 境内云端 LLM（OpenAI 兼容接口，服务器在境内） | 需显式配置才启用 | 🟡 可做但有条件 | ① 属委托处理，需 DPA；② 需告知并取得合法性基础；③ 要求云厂商不保留、不用于训练（书面）；④ 传输加密；⑤ 发送前脱敏；⑥ 医院书面批准；⑦ 全量留痕。**须律师确认** |
| **境外云服务 / 境外服务器** | 未启用 | ❌ **建议直接禁用** | 触发数据出境路径（安全评估/标准合同/认证）；医疗健康数据出境门槛高。**建议在配置层硬禁并从文档中删除该选项** |
| 境外远程运维/排障 | ⚪ 未确认 | ❌ 禁用 | 若需，先脱敏 + 走 §5.5 审批 |
| 境外代码托管与 CI | 项目使用 GitHub 与 CI 构建 | ⚪ **需核实** | 若仓库、构建产物、issue 中含真实报告样本（哪怕"脱敏样例"），即构成数据出境风险。**建议核实仓库与 CI 中是否存在任何真实报告数据，并删除/替换为合成数据** |
| 使用院内报告做模型微调 | 有 `train/`、`adapters/`、微调方案文档 | ⚪ **高风险，需核实** | 训练数据来源必须可追溯；若含真实报告，需伦理审批 + 单独授权 + 去标识 + 本地训练。**须律师与医院伦理确认** |
| 开源仓库的样例数据 | 仓库含数据集调研与标注范式文档 | ⚪ 需核实 | 确保公开仓库中**零真实 PHI**；建立"提交前 PHI 扫描"检查 |

## 6. 里程碑建议

> 两条路线**不是互斥的**，但**不能同时对外承诺**。建议：**先按路线 A 收紧口径与数据合规并开始商用**，同时**并行推进路线 B 的前置判断（分类界定）**；分类界定结论出来后立即决定是否切换。

### 6.0 两条路线的关键差异与共同底座

| 项 | 路线 A：非器械定位先商用 | 路线 B：器械注册路径 |
|----|--------------------------|---------------------|
| 前提 | 分类界定/法律意见确认非器械，或严格限定为质量管理/科研用途 | 落入器械定义，按二类注册 |
| 首个外部动作 | 法律意见 + 分类界定咨询 | 分类界定申请 + 注册顾问签约 |
| 能否收费商用 | 可以（软件订阅），但文案受限 | 取得注册证后方可临床销售 |
| 共同底座 | §3.0 定位收敛、§3.3 数据合规、§5 全部专项、代码签名、应急预案 | 同左，另加 §3.1 体系与临床 |

### 6.1 路线 A：可先商用（非器械定位）

| 里程碑 | 时间 | 交付物 | 关键依赖（含外部） |
|--------|------|--------|-------------------|
| **A0 定位收敛与止血** | 0–1 个月 | ① 统一对外用途声明（README/DISCLAIMER/官网/UI/话术）；② 律师出具"非器械定位可行性"意见（⚠️**需外部**）；③ 日志 PHI 硬校验上线；④ 隐私政策/数据安全白皮书与实现对齐 | 律师（外部）；内部 1–2 人周 |
| **A1 数据合规底座** | 1–3 个月 | ① 数据分级制度 + 数据字典；② 备份加密 + 恢复演练；③ 诊断包加密 + 审计留痕；④ 数据导出审批表（一页纸）常态化；⑤ PIA 报告（⚠️**需外部**律师复核） | 律师（外部）；医院信息科（若试点） |
| **A2 安全准入准备** | 3–6 个月 | ① 系统定级（⚠️**需外部**定级/测评机构）；② 等保差距评估与整改（按定级结论，二级或三级）；③ 多机部署加固包（TLS/反代模板/端口最小化）；④ 权限矩阵 + 越权测试；⑤ 应急预案与一次演练 | 测评机构（外部）；医院信息科（外部） |
| **A3 商用与试点** | 6–9 个月 | ① 代码签名证书与分发校验；② 与 1–3 家医院完成**科研/质量管理用途**试点（⚠️**需外部**：医院同意 + 伦理/科研审批，若涉及研究数据）；③ 试点报告与反馈闭环；④ 合同/DPA/服务条款定稿 | 医院（外部）；律师（外部） |
| **A4 规模化前提** | 9–12 个月 | ① 等保测评（若定级要求）或医院准入材料包；② 医院准入清单（软件准入 + 网络安全 + 数据安全）逐项通过；③ 第三方渗透测试报告（建议）；④ 若分类界定结论为"属器械"，**立即转入路线 B** | 测评机构、渗透测试机构（外部）；医院信息科（外部） |

**A 路线的红线**：不得进入"与诊断决策绑定"的场景（如质控结果阻断报告签发、写入诊断内容）；一旦医院要求此能力，A 路线的法律基础即失效，必须走 B。

### 6.2 路线 B：器械注册路径

| 里程碑 | 时间 | 交付物 | 关键依赖（含外部） |
|--------|------|--------|-------------------|
| **B0 判定与立项** | 0–2 个月 | ① 分类界定申请与答复（⚠️**需外部**药监/标管中心）；② 注册顾问签约（⚠️**需外部**）；③ 注册路径与临床评价策略确定；④ 预算与人力立项 | 注册顾问（外部）；省级药监局（外部） |
| **B1 体系与文档** | 2–6 个月 | ① ISO 13485 质量体系建立（⚠️**需外部**咨询/认证机构）；② 风险管理报告（GB/T 42062）；③ 软件生存周期与安全分级（YY/T 0664）；④ 软件描述文档 + 网络安全描述文档（M5/M7）；⑤ 产品技术要求 | 质量体系咨询机构（外部）；注册顾问（外部） |
| **B2 检验与临床** | 4–10 个月 | ① 注册检验报告（⚠️**需外部**有资质检验机构，排队+检测 2–4 个月）；② 临床评价资料：同品种比对**或**临床试验（⚠️**需外部**伦理委员会、临床试验机构，若做试验 **6–18 个月**）；③ 注册申报资料全套撰写 | 检验机构、伦理委员会、临床机构（外部） |
| **B3 申报与审评** | 10–18 个月 | ① 提交注册申请（省级药监局）；② 技术审评 + 发补答复（⚠️**需外部**，可能 1–3 轮）；③ 质量管理体系核查；④ 取得注册证 | 省级药监局、审评中心（外部） |
| **B4 上市后** | 18 个月起 | ① 不良事件监测流程；② 变更控制与网络安全更新机制；③ UDI（若适用）；④ 说明书/标签定稿与培训材料 | 监管机构（外部） |

**诚实的周期判断**：**二类器械注册从零到拿证，12 个月是极限乐观、12–24 个月是现实区间**，其中临床评价（若需临床试验）与审评发补是最大不确定项。**不要把"12 个月拿证"写进商业计划或投资人材料。**

| 术语 | 含义 |
|------|------|
| SaMD | Software as a Medical Device，作为医疗器械的软件（独立软件） |
| PHI | Protected Health Information，受保护的健康信息（本文泛指可识别到个体的医疗健康数据） |
| PIA | 个人信息保护影响评估 |
| DPA | 数据处理协议（Data Processing Agreement） |
| 等保 2.0 | 网络安全等级保护 2.0 系列标准（GB/T 22239-2019 等） |
| 密评 | 商用密码应用安全性评估 |
| 分类界定 | 就某产品是否属医疗器械、属第几类，向药监部门申请判定 |
| 三员 | 系统管理员、安全管理员、审计管理员（等保三级职责分离要求） |
| 定级 | 按 GB/T 22240 确定信息系统安全保护等级 |
| SBOM | 软件物料清单（Software Bill of Materials） |
