## 2. 冲突在哪（一句话）

> 同一个仓库里，`LICENSE` 说"任何人都可以自由使用、修改、再分发乃至**销售**"，
> 而 `TERMS_OF_SERVICE` 说"要按 ¥59/年订阅、激活码绑定、**禁止修改和分发**"。
> 两份文档互相打架，而**对已公开的版本，MIT 优先且不可撤销**。

具体后果（按严重度）：

1. **付费理由被自己削弱**：医院信息科/采购只要点开仓库就能看到 MIT —— 可自行部署、内部扩散、二次开发。你收年费的正当性需要额外解释（"卖的是服务/更新/签名/实施"，而非软件使用权）。
2. **竞争者可以合法复刻**：MIT 明文允许 "sublicense, and/or sell"。别人可以改名销售，或构建一个**去掉激活校验**的版本（MIT 允许修改），你不构成被侵权——因为是你自己授权的。
3. **激活码体系与许可自相矛盾**：Ed25519 卡密只能约束"愿意遵守约定的人"；在 MIT 之下，绕过校验对**已发布版本**不构成许可违约。
4. **条款可能被判不可执行**：ToS §7.2 禁止的行为恰是 LICENSE 明确授予的，冲突条款在争议中通常不利于起草方（你）。
5. **不可撤销**：MIT 一经公开即对**所有已发布提交/版本永久生效**；换许可**只对之后的版本有效**。别人在此之前 fork 的快照，永远保留 MIT 权利。
6. **发布物本身也在授权**：exe/zip 里带着 `server/*.py` 源码，等于"二进制 + 源码"双重公开。

**好消息**：目前 0 fork / 0 star / 1 次下载、且**没有真实收款** → 这是成本最低的修正窗口，现在改几乎无痛。

## 3. 选项（含代价）

### 选项 A（推荐）：改为专有 / 源可见许可，保留订阅与激活
把 `LICENSE` 换成下面之一（按推荐的宽松度排序）：

| 候选 | 语义 | 适配度 |
|---|---|---|
| **PolyForm Noncommercial 1.0.0** | 允许**非商业**（科研/教学/个人）使用与修改；**商业使用需另行授权** | ★★★ 与"实验性质 + 医院付费"最契合：学术可自由用，医院商用要签约 |
| **BSL 1.1**（Business Source License） | 生产使用受限，**N 年后自动转为开源**（如 Apache-2.0） | ★★ 兼顾"将来开源"的叙事；需指定变更日期与变更后许可 |
| **Elastic License 2.0** | 允许使用/修改，**禁止把本软件作为托管服务对外提供** | ★★ 若担心被做成 SaaS 竞品 |
| **保留所有权利 + 订购协议/EULA** | 最严；使用者仅在合同范围内可用 | ★ 控制力最强，但与"实验性质、想被更多人用"的初衷相悖 |

- 收益：与激活码、订阅、退款政策自洽；医院采购习惯"合同 + 发票 + 售后"；阻断改名销售。
- 代价：不再是开源项目（失去开源声誉与外部贡献）；需重写 `DISCLAIMER`/`README`/ToS 的许可段；**必须**写一份 `LICENSE-HISTORY.md` 说明"哪些版本仍是 MIT"，避免追溯争议。
- 技术上必须注意：**自动更新依赖匿名可下载的 Release**，而**私有仓库的 Release 不对外** → 若要把源码转私有，需另建一个"只放产物"的公开仓库（如 `report-qc-releases`），源码留私有。这是选项 A 的**配套工程改动**（工作量：半天）。

### 选项 B：保持 MIT，只卖服务
- 只卖实施/培训/运维/定制，**放弃"按账号订阅 + 激活码"的商业模型**（激活体系变成摆设，或仅作"试用期管理"）。
- 适合走"影响力 / 咨询 / 项目制"路线；不适合按席位收费。

### 选项 C：双许可（开源版 + 商业版）
- 例：`AGPL-3.0`（或更弱的 OSS 许可）+ 商业许可；或 MIT 基础版 + 商业增强版。
- 注意：AGPL 的"网络条款"对**院内自用**不触发，医院没有付费动力；要靠"增强功能"（如质控台账、报表、RIS 集成）区分版本。
- 需要 CLA（若接受外部贡献）+ 律师起草；成本最高。

### 选项 D：维持现状（不推荐）
- 无法律手段阻止 fork/改名/去校验分发；ToS 与 LICENSE 的冲突持续存在。

## 4. 无论选哪个，都建议立刻做的 4 件小事

1. **补 `LICENSE-HISTORY.md`**：写明"MIT 适用于 vX.Y.Z 及更早版本的公开发布；自 vA.B.C 起改为 <新许可>"。这是**事实声明**，能显著降低追溯争议。（已由本轮审计添加初版，待定稿。）
2. **改掉 ToS §7.2 与 LICENSE 的正面冲突**：在最终选型前，先把口径改成"服务范围按本条款；软件本身的使用许可以仓库 LICENSE 为准"（本轮已在 `TERMS_OF_SERVICE.md` 顶部加提示）。
3. **发布物里放一份 `LICENSE` + `免责声明` + `版本号`**：现在用户拿到的是裸 exe/zip；至少让他第一眼知道"实验性软件、不用于临床诊断、许可是什么"。
4. **把实验性质与不做临床用途承诺写进订购协议**：D1 定为"实验性质"后，卖的是"服务与更新"，不是"医疗质量担保"。

> ⚠️ 以上选项的**最终文本必须经律师定稿**（一次性 1–2 小时咨询即可）。
> 关键约束：换许可只保护**将来**；拖延的每一天都在为"已授予 MIT"的范围背书。
